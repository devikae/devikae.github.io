대표 사례: 댓글 조회 구조를 세 가지로 측정해 고르기

문제
글 하나의 댓글을 모두 읽어 메모리에서 트리를 조립하는 구조였습니다. 댓글이 늘면 응답 크기와 메모리 사용량이 함께 커졌고 페이징도 적용할 수 없었습니다.
판단
세 가지 구조를 각각 브랜치로 만들어 같은 조건(MySQL 8, 댓글 1,000건, 분산 데이터와 핫스팟 데이터)에서 측정했습니다. 대댓글을 한 번에 읽는 방식은 대댓글이 몰린 글에서 응답이 103.70KB로 다시 커져 제외했습니다. 루트 댓글 20건과 루트별 대댓글 5건만 먼저 보내고 나머지는 더보기 API로 나누는 방식을 택했습니다.
감수
분산 데이터에서는 제외한 방식보다 조금 느립니다(14.6ms 대 10.3ms). 대신 응답 크기가 절반 가까이 작고(22.03KB 대 39.87KB), 대댓글 전용 API를 하나 더 관리합니다.
결과
대댓글이 몰린 글에서 읽은 행이 1,000건에서 25건으로, 응답 크기가 205.84KB에서 5.55KB로, 실행 시간이 35.4ms에서 5.6ms로 줄었습니다. 별도 실험에서는 100만 건 합성 데이터에 복합 인덱스를 적용해 읽은 행을 200,001건에서 2,000건으로 줄였습니다.

데이터 정합성

  • 추천 수 갱신 방식으로 낙관적 락, 비관적 락, 원자적 UPDATE를 비교하고 단순 증감에는 원자적 UPDATE를 택했습니다. 추천을 PUT/DELETE로 정의해 같은 요청이 재시도되어도 한 번만 반영되게 했습니다. (동시 요청 100건, 같은 회원 100회 반복, 추천과 취소 혼합 조건을 각 3회 실행해 모두 일치)
  • 목록에서 매번 COUNT, GROUP BY로 세던 댓글 수와 추천 수를 컬럼으로 옮기고 원본과 같은 트랜잭션에서 갱신했습니다. 값이 어긋날 때를 대비해 CHECK 제약과 관리자 보정 경로를 두었습니다.
  • 내부 조인에는 BIGINT PK를 쓰고 API에는 UUID만 노출했습니다. 회원과 스키장의 관계는 중계 엔티티로 분리하고 복합 UNIQUE 제약으로 중복 저장을 막았습니다.

외부 연동과 권한

  • 카카오 경로 API와 유가 정보 API 호출을 DB 트랜잭션 밖으로 옮겼습니다. 외부 응답 대기와 내부 저장을 분리하고, 외부 호출 실패 시 일부 데이터만 저장되지 않는지 검증했습니다.
  • 외부 호출이 모두 실패하면 허용 범위를 통과한 사용자 입력만 저장하고 값의 출처와 계산 시점을 함께 기록했습니다.
  • Google, Naver OAuth 2.0 로그인을 기존 회원 연결과 신규 가입 흐름에 통합했습니다. 일회성 state와 로그인 시 세션 ID 교체를 적용했습니다. (테스트 22건)
  • 공개 채팅방에 답하는 AI(MCP)에는 회원과 원본 채팅에 묶인 60초 읽기 전용 토큰만 발급했습니다. 관리자가 호출해도 일반 사용자 권한으로 제한됩니다. (거부 시나리오 테스트 13건)

배포와 운영

  • 운영 EC2에서 하던 이미지 빌드를 GitHub Actions로 옮기고 ECR 이미지 digest로 배포 대상을 고정했습니다. AWS OIDC와 SSM으로 SSH 포트와 PEM 키 없이 배포했습니다. 직전 버전 복구 뒤 외부 응답과 재배포를 확인했으며, 측정한 SSM 롤백 구간은 19초입니다.
  • 라이브톡은 Spring SimpleBroker와 최근 30건의 인메모리 버퍼로 RDB와 분리했습니다. 로컬에서 200명이 5회씩 보내는 부하 테스트를 실행해 수신 200,000건, 누락 0건, 수신 p95 951ms를 확인했습니다.
  • Pinpoint를 별도 EC2에 10% 샘플링으로 연결해, DB 장애 때 커넥션 획득을 30초 기다리는 구간을 요청 단위로 확인했습니다.
  • AI가 작성한 코드 초안은 설계 문서와 계층 규칙에 맞는지 검토하고 테스트와 실제 배포로 확인한 뒤 반영했습니다.
