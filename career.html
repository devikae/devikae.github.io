1. 커서 페이지네이션과 복합 인덱스 기반 댓글 조회 성능 검증

문제
댓글 전체를 읽어 메모리에서 트리로 조립해 응답 크기와 메모리가 댓글 수에 비례했고, 페이징도 없었습니다.
판단
전체 조립, 루트 커서+대댓글 일괄 조회, 루트 20건+대댓글 5건과 더보기 API를 브랜치로 구현해 분산 데이터와 쏠림 데이터에서 비교했습니다. 일괄 조회는 쏠림에서 103.70KB로 커져 제외했습니다. 2단계 답글에는 Recursive CTE와 Closure Table이 과하다고 보고 측정 전에 제외했습니다.
제약
분산 데이터에서는 비교안보다 느립니다(14.6ms 대 10.3ms). 별도 대댓글 API도 관리합니다. 100만 건 실험에서 LIMIT 전 JOIN과 정렬로 루트 20,000행을 읽는 병목(평균 36.6ms)을 찾았고, 개선안 3개는 문서로만 남겨 아직 미적용입니다.
검증
쏠림 데이터에서 반환 행 1,000→25건, 응답 205.84→5.55KB, 실행 35.4→5.6ms (MySQL 8, 댓글 1,000건, 단일 실행 PoC). 별도 100만 건 합성 데이터의 복합 인덱스 비교에서는 읽은 행 200,001→2,000건, 평균 226.22→102.47ms, p95 241.63→115.88ms (워밍업 5회 후 20회, 쿼리 시간만).

2. 원자적 UPDATE와 락 순서 통일 기반 추천 카운터 동시성 제어

문제
100개 트랜잭션이 동시에 카운터 0을 읽도록 재현하자 추천은 100건인데 카운터는 1이었습니다. 토글 API는 재전송하면 반대 상태가 됐습니다.
판단
100스레드, 각 3회로 원자적 UPDATE, 낙관적 락, 비관적 락을 비교했습니다. 낙관적 락은 약 4,950회 재시도, 2.8~3.0초, 원자적 UPDATE는 436~467ms였습니다. 비관적 락과 시간은 비슷해 단순 증감에는 원자적 UPDATE를 택하고 API는 PUT/DELETE로 나눴습니다.
제약
같은 글의 쓰기는 row 락에서 직렬화됩니다. 중복 PUT은 증가 후 복구해 UPDATE가 두 번입니다. INSERT→UPDATE에서 FK 공유 락이 배타 락으로 승격되며 난 데드락은 모든 경로가 게시글 row를 먼저 잡도록 순서를 통일해 해결했습니다.
검증
실제 테이블 통합 테스트에서 서로 다른 회원 100명, 동일 회원 100회, PUT/DELETE 혼합 등 7개 시나리오를 각 3회 실행해 오류 0건과 원본과 카운터 일치를 확인했습니다. 강제 실패 시 동시 롤백과 UNIQUE, CHECK 제약도 검증했습니다.

3. Idempotency Key와 응답 스냅샷 기반 중복 요청 처리

문제
커밋 후 응답 유실로 재요청하면 글이 중복 저장됩니다. 대상은 게시글, 댓글, 설질 제보, 카풀, 장터 5종입니다.
판단
공통 기록표에 첫 응답 JSON을 저장해 수정, 삭제 후에도 같은 응답을 돌려줍니다. 서비스 5곳을 개별 수정하는 대신 컨트롤러 TransactionTemplate에 합류시켰고, 키는 HMAC 해시로 저장합니다.
제약
키가 있는 카풀 등록은 외부 조회까지 같은 트랜잭션에 들어갑니다. 앞서 분리했던 호출을 재합류시킨 선택입니다. 시간당 10건 제한을 근거로 영향을 작게 판단했으나 커넥션 점유 시간은 미측정입니다.
검증
통합 테스트 13건. 같은 키의 8스레드 요청이 모두 201로 응답하고 글과 기록은 각 1건이었습니다. 대댓글 재전송 검증 중 벌크 쿼리가 변경 감지를 무력화하는 버그도 찾아 수정했습니다.

그 밖의 데이터 처리

  • 외부 API: 카카오 길찾기 최대 2회와 오피넷 1회를 호출합니다. 헤더 없는 등록, 수정, 미리보기는 계산과 저장을 별도 빈으로 분리합니다. 운영 커넥션 풀은 10개입니다.
  • 정렬: CSV 이관 후 ID와 작성 시각 순서가 달라진 오류를 작성 시각 정렬과 커서로 수정하고 운영 공개글 80건의 누락과 중복을 전수 확인했습니다.
  • 테스트 DB: LATERAL, FK 락, CHECK 검증을 위해 H2를 제거하고 테스트와 CI를 MySQL로 통일했습니다.
  • 식별자와 관계: 내부 BIGINT PK와 공개 UUID를 분리하고 권한은 별도로 검사합니다. 회원과 스키장 중계 엔티티에 복합 UNIQUE를 적용했습니다.

4. Transactional Outbox와 SKIP LOCKED 기반 검색 색인 동기화

문제
원문의 비동기 복제본인 검색 색인이 이벤트 유실, 중복, 역순과 처리 중 종료에도 원문을 따라가야 했습니다.
판단
커밋 직후 종료 시 유실되는 AFTER_COMMIT 비동기와 JPQL 일괄 UPDATE를 놓치는 엔티티 리스너를 제외했습니다. 원문 트랜잭션에 Outbox를 쓰고 FOR UPDATE SKIP LOCKED와 lease로 처리합니다. 이벤트에는 ID와 버전만 담고 원문을 재조회해 중복, 역순을 멱등 처리합니다. Debezium과 Kafka는 도입하지 않았습니다.
제약
새 쓰기 경로의 기록 누락은 매일 대조 작업으로 보완해 최대 하루 지연될 수 있습니다. 색인 본문만 손상된 경우는 대조로 찾지 못합니다.
검증
통합 테스트 11건으로 중복, 역순, 삭제 후 옛 수정, 재시도, lease 만료를 확인했습니다. 반영 지연 p95는 폴링 1초에서 939.8ms, 200ms에서 197.6ms (로컬, 글 1건 100회 수정, 각 1회). 운영 지연은 미측정입니다.

5. STOMP SimpleBroker 기반 실시간 채팅과 재연결 제어

문제
현장 동행과 설질 정보를 바로 주고받을 실시간 대화가 필요했고, 앱 서버는 RAM 2GB EC2 1대였습니다.
판단
Raw WebSocket의 세션과 방 구현 비용, SSE+POST의 이중 채널, Redis의 비용과 동일 EC2 메모리 위험, 외부 SaaS의 링크 차단과 감사 제약을 비교해 STOMP SimpleBroker를 택했습니다. 대화 본문은 DB에 저장하지 않고 최근 30건만 메모리에 둡니다. 10초 heartbeat와 지수 백오프와 지터로 재연결을 제어합니다.
제약
재배포 시 대화가 사라져 화면에 안내합니다. 서버를 늘리면 메시지와 로컬 상태 공유를 위한 Redis 전환이 필요합니다.
검증
가상 사용자 200명이 5회씩 발송해 수신 200,000건, 누락 0건, 수신 p95 951ms, 힙 309MB였습니다. 300명은 p95 2,115ms, 400명은 4,517ms로 측정돼 실험 목표선을 200명으로 정했습니다 (로컬, 서버와 부하 발생기 동일 JVM, 단계별 1회). 운영 용량을 의미하지 않습니다.

6. OAuth 2.0 제공자와 사용자 ID 기반 계정 식별과 세션 보안

문제
첫 Google, Naver 로그인은 같은 이메일의 기존 회원과 자동 연결했습니다. 이메일 문자열로 계정 권한을 얻거나, 비권위 이메일로 일반 가입과 비밀번호 재설정 대상을 선점할 위험이 있었습니다.
판단
머지 다음 날 provider+고유 ID로 로그인 권한을 판단하도록 바꿨습니다. Google은 검증된 Gmail과 Workspace 도메인만 권위 이메일로 보고 충돌 시 거절합니다. Naver와 그 외 이메일은 내부 식별 이메일을 쓰고 실제 값은 별도 보관합니다.
제약
같은 이메일의 기존 회원은 소셜 로그인을 바로 쓸 수 없고 수동 연결 기능도 없습니다. 이미 연결된 데이터는 정상 연결을 끊을 수 있어 일괄 분리하지 않았습니다.
검증
OAuth 테스트를 22→31건으로 늘리고 일회성 state와 로그인 시 세션 ID 교체를 적용했습니다. 제공자 호출은 Mock 기반 단위 테스트입니다.

7. 단기 토큰, Scope, 경로 Allowlist 기반 채팅 AI 접근 제어

문제
공개 채팅 봇이 공용 또는 관리자 계정으로 API를 쓰면 권한이 과도하고 답변은 모두에게 공개됩니다.
판단
사용자 권한, 도구 허용 목록, scope의 교집합만 위임합니다. 토큰 발급과 검증은 Spring에 두어 Node 봇과 서명 비밀을 공유하지 않습니다. 60초 읽기 전용 토큰으로 GET과 경로 8개만 허용하고 관리자 호출도 일반 사용자 권한으로 낮춥니다.
제약
무상태 토큰이므로 유효한 60초 안의 재사용은 막지 않습니다.
검증
토큰과 필터 테스트 13건(거부, 실패 시나리오 11건)을 통과했습니다. 기능 플래그는 기본 꺼짐이며 실제 모델 답변 품질은 검증 범위 밖입니다.

8. ECR Digest, AWS OIDC와 SSM 기반 배포 및 롤백

문제
EC2 직접 빌드로 CI 검증 산출물과 운영 이미지의 동일성을 확인할 수 없었고, 과거 이미지를 그대로 재실행할 수도 없었습니다.
판단
Actions에서 빌드하고 ECR digest로 배포 대상을 고정해 OIDC와 SSM으로 배포합니다. 대기 중 새 push로 이미지와 compose가 어긋나지 않게 커밋 SHA도 고정했습니다. 과거 소스 재빌드는 같은 바이트를 보장하지 않아 롤백에서 제외했습니다. ECS, Fargate와 설정 release artifact는 현재 규모에 비용과 범위가 과하다고 판단했습니다.
제약
ECR 수명 주기와 태그를 관리해야 합니다. 단일 컨테이너 교체여서 무중단이 아니며 앱만 롤백하므로 스키마 변경 시 호환성을 먼저 확인합니다.
검증
프런트 1회 실제 롤백: SSM 단계 19초, 워크플로 전체 27초, 재배포 21초와 31초를 Actions 기록으로 확인하고 외부 API 200을 대조했습니다. 장애 인지와 판단 시간은 제외합니다. 빌드, push, 배포는 약 2분입니다.

9. RDS IAM 인증과 전용 계정 기반 DB 마이그레이션 권한 분리

문제
앱 계정에는 DDL 권한을 주지 않고 ddl-auto=validate를 유지하면서 운영 스키마를 변경해야 했습니다.
판단
앱 시작과 분리한 전용 마이그레이션을 선택했습니다. 전용 계정, RDS IAM 인증과 checksum을 검사하는 runner를 만들어 앱 배포 전에 실행합니다. GitHub Environment 승인을 거치며 적용된 파일이 바뀌면 중단합니다.
제약
runner를 직접 유지합니다. SQL 실행과 이력 기록이 한 트랜잭션이 아니므로 SQL을 멱등하게 작성하며, 실패 시 자동 역변경 없이 forward fix로 대응합니다.
검증
변수 누락으로 마이그레이션이 앱 배포 전에 실제 중단됐고 약 1시간 뒤 수정 후 재실행했습니다. CI의 임시 MySQL에서 전체 적용과 재실행을 검증합니다.

10. 행 잠금과 Lease 기반 S3 고아 객체 정리

문제
글 저장 전 업로드한 사진은 취소하면 고아 객체로 남습니다. 정리와 글 저장이 겹치면 방금 연결한 사진을 지울 수 있고 DB와 S3는 같은 트랜잭션이 아닙니다.
판단
정상 이미지까지 지울 수 있는 폴더 전체 Lifecycle을 제외했습니다. 업로드 전 PENDING 행을 만들고, 정리는 행 잠금 안에서 DELETING과 10분 lease를 표시한 후 S3 삭제를 트랜잭션 밖에서 수행합니다.
제약
DB 상태 전이와 S3 삭제가 분리돼 있어 두 단계의 처리 상태를 관리해야 합니다. 검증 당시 운영 객체는 6개 규모였습니다.
검증
리뷰에서 본문에만 쓰인 사진이 정리되는 결함을 찾아 참조 표를 추가했습니다.

MySQL 행 잠금과 고정 윈도우 기반 업로드 요청 제한

재시작하면 사라지는 메모리 한도 대신 MySQL 행 잠금으로 고정 창 요청 제한을 구현했습니다. Redis는 추가하지 않았습니다. 한도 5에 동시 요청 20건을 보내 5건만 허용되고 저장소 장애 시 차단됨을 통합 테스트로 확인했습니다.

요청마다 DB 쓰기와 잠금 비용이 발생하며 부하는 아직 측정하지 못했습니다. 이 제한으로 공개 CDN 다운로드 비용의 절대 상한을 보장하지는 못합니다.

AI 활용 개발의 설계 판단과 검증 절차

Linear 티켓에 배경, 목표, 범위, 완료 조건을 정의하고 구현과 기록을 AI 에이전트에 맡깁니다. 무엇을 만들지와 어떤 방식을 택할지는 제가 결정하며, AI가 작성한 코드는 직접 검토하고 검증합니다.

  • 대안 선택: 에이전트의 설계안 2~3개를 비교하고 요구사항에 맞지 않으면 요구사항을 조정해 다시 설계하게 합니다. 성능과 정합성 선택은 같은 조건의 측정 결과를 확인한 뒤 결정합니다.
  • 검증과 리뷰: 결정 이유, 변경 범위, 테스트 결과를 확인하고, 리뷰 지적은 코드와 대조해 수정, 보류, 반박으로 나눕니다. 독립 작업은 worktree별 에이전트에 나눠 진행합니다.
  • 작업 규칙: AGENTS.md를 입구로 프로젝트 규칙과 분야별 문서를 관리합니다. 작업에 필요한 문서만 참조하게 하고, 결과가 기준에서 벗어나면 규칙을 수정합니다.
