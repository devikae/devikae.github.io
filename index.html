01추천 · 동시성

100명이 동시에 추천을 누르면 숫자가 어긋나고 데드락이 나던 문제

문제

100명 동시 추천에서 추천 행은 100개인데 like_count는 1만 올라가는 Lost Update를 재현했습니다. 추천 행을 넣을 때 InnoDB가 부모 글에 S-Lock을 걸고, 이어서 카운터를 올리려 X-Lock으로 승격하는 순간 데드락도 났습니다.

검토한 방법

기각낙관적 락 + 재시도2,998ms · 재시도 4,950회
기각비관적 락 SELECT FOR UPDATE455ms · 락 대기 관리
채택원자적 UPDATE + 부모 X-Lock 선점440ms · 재시도 0회

해결

취소도 같은 순서로 맞추고, 토글 POST를 멱등한 PUT/DELETE로 나눴습니다. 음수 감산은 조건부 UPDATE, CHECK 제약, 대사 로직으로 막았습니다.

Lost Update 0건, 추천 50 + 취소 50 혼합 부하 데드락 0건. 동일 요청 100회 중복 반영도 0건이었습니다.

Testcontainers MySQL 8.0 · 방식별 3회 반복 · PR #25, #26

02댓글 · 쿼리 성능

1,000건 테스트로는 보이지 않던 댓글 조회 병목을 100만 건에서 찾은 과정

문제

댓글 1,000건은 버퍼 풀에 다 올라가 인덱스가 없어도 0.3ms에 끝났습니다. 나쁜 쿼리가 숨는다고 보고, 인기글 한 개에 댓글 10%가 몰리는 편중 시드로 1K부터 1M까지 만들었습니다.

검토한 방법

기각전체 조회 후 메모리 트리 조립초기 응답 210KB
기각ROW_NUMBER() 윈도우 함수대댓글 2,000건 정렬
채택루트 20개 커서 + LATERAL Top-5루프당 5건에서 종료

해결

EXPLAIN ANALYZE에서 노드별 actual rows × loops를 읽어 LATERAL이 루트마다 5건에서 멈추는 것을 확인했습니다. 정렬을 없애려 4컬럼 인덱스를 만들면 쓰기마다 페이지 분할 비용이 커져서, 0.1~1.5ms filesort는 받아들이고 3컬럼 인덱스를 유지했습니다.

원댓글 첫 페이지 226.22ms → 36.58ms. 대댓글 Top-5는 1K부터 1M까지 0.48ms로 일정했습니다.

9개 시나리오 × 4개 규모 · 워밍업 5회, 측정 20회 · PR #18

03배포 · 복구

EC2에서 직접 빌드하다 디스크가 99% 찬 배포 구조를 바꾼 일

문제

2GB 메모리 EC2에서 이미지를 빌드하니 빌드 캐시가 24GB 쌓였고, 남은 공간이 287MB까지 줄었습니다. latest 태그는 덮어써져서 직전 정상 버전을 정확히 찾을 수도 없었습니다.

검토한 방법

기각SSH 접속 + 서버 내부 빌드빌드마다 결과가 다름
기각ECR latest 태그 + SSH 배포롤백 대상 식별 곤란
채택OIDC + ECR digest + SSM22번 포트, 정적 키 없음

해결

장기 액세스 키 대신 OIDC 임시 자격증명을 쓰고, SSH 포트를 닫은 채 SSM으로 배포합니다. RDS 스냅샷으로 임시 인스턴스를 띄우는 복구 훈련도 했습니다.

디스크 21GB 확보. 직전 digest로 되돌린 뒤 외부 API 200 응답을 확인했고, SSM 배포 구간은 19초였습니다.

AWS EC2 · ECR · SSM · RDS · PR #19, #27, #33

04

외부 거리 API를 기다리는 동안 DB 커넥션이 묶이던 카풀 정산

외부 API 대기 중 커넥션 점유 0ms, 저장할 때만 약 5ms+

문제

카풀 글을 쓰면 카카오 경로 API 2회와 오피넷 유가 API를 호출해 1인당 비용을 계산합니다. 서비스 전체에 트랜잭션을 걸면 2~3초 동안 커넥션을 잡고 있어, 동시에 10명만 써도 커넥션 풀이 바닥납니다.

검토한 방법

기각서비스 전체 @Transactional커넥션 고갈
기각글 먼저 저장 후 비동기 계산비용 없는 글 노출
채택외부 호출과 저장 빈 분리INSERT 시에만 점유

해결

외부 호출은 트랜잭션 밖에서 끝내고 계산 결과만 저장 빈에 넘깁니다. 금액은 BigDecimal 올림 정책과 Math.addExact로 계산해 스냅샷으로 남기고, API가 실패하면 직접 입력으로 넘어갑니다. 유가는 Caffeine으로 캐시했습니다.

Kakao Mobility · 오피넷 · Caffeine · PR #34

05

서버 한 대로 실시간 대화를 몇 명까지 받을 수 있는지 먼저 정한 일

200명 × 5라운드 20만 건 누락 0건, 수신 p95 951ms+

문제

STOMP 방송은 접속자가 늘면 전송량이 제곱으로 늘어납니다. Redis Pub/Sub부터 들이기 전에, 지금 서버 한 대로 감당할 수 있는 선을 숫자로 알아야 했습니다.

검토한 방법

기각Redis Pub/Sub 선도입아직 필요 없는 인프라
기각대화 전체 RDB 저장게시글과 커넥션 경쟁
채택SimpleBroker + 최근 30건 메모리 보관부하 테스트로 한계 측정

해결

100명부터 400명까지 5단계로 부하를 걸어 안전 용량을 200명으로 정했고, 넘으면 스키장별 채널 분리 다음 Redis로 확장합니다. 감사 로그는 대화 본문 대신 접속과 종료만 비동기로 남겨 96% 줄였습니다.

ChatLoadTest · Nginx WebSocket 핫픽스 · PR #22, #23, #24

06

비밀번호 재설정 응답 시간으로 가입 여부가 드러나던 문제

응답 내용과 시간 어느 쪽으로도 계정 존재 여부 구분 불가+

문제

가입된 이메일은 SES 발송 때문에 약 350ms, 미가입 이메일은 5ms 만에 응답했습니다. 문구를 같게 해도 응답 시간으로 가입 여부를 알 수 있었습니다.

해결

가입 여부와 관계없이 같은 202 응답을 주고, 응답 시간을 최소 400ms에 무작위 0~100ms를 더해 맞췄습니다. 인증 코드는 용도와 이메일을 묶은 HMAC-SHA256으로 저장하고 상수 시간으로 비교합니다. 재설정이 끝나면 그 회원의 HTTP 세션과 WebSocket을 모두 끊습니다.

AWS SES v2 · MessageDigest.isEqual · PR #35, #37
