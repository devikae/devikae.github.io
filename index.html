추천 · 동시성

추천을 동시에 누르면 숫자가 틀어지고 데드락이 나던 문제

문제

100명이 동시에 추천하면 추천 기록은 100개인데 추천 수는 1만 올라갔습니다. 추천 기록을 넣을 때 MySQL이 게시글 행에 공유 락을 겁니다. 바로 뒤에 추천 수를 올리려고 배타 락을 요청하는 순간 두 요청이 서로를 기다리면서 데드락도 났습니다.

검토한 방법
  • 기각
    낙관적 락 + 재시도 · 2,998ms, 재시도 4,950번
  • 기각
    비관적 락 (SELECT FOR UPDATE) · 455ms, 락 대기를 따로 관리
  • 채택
    추천 수를 먼저 올려 락 순서 고정 · 440ms, 재시도 없음
해결

게시글 추천 수를 먼저 올려 배타 락을 잡고 그다음에 추천 기록을 넣도록 순서를 바꿨습니다. 취소도 같은 순서로 맞췄습니다. 같은 요청이 두 번 와도 결과가 같도록 토글 POST를 PUT과 DELETE로 나눴습니다. 추천 수가 음수가 되지 않게 조건부 UPDATE와 CHECK 제약을 걸었습니다.

그만큼 한 글에 몰린 요청은 한 줄로 서서 처리됩니다. 추천은 몇 ms 늦어도 괜찮지만 숫자가 틀리면 안 된다고 판단했습니다.

결과

숫자 틀어짐 0건. 추천 50번과 취소 50번을 섞은 부하에서도 데드락 0건이었습니다.

댓글 · 쿼리 성능

데이터 1,000건에서는 안 보이던 댓글 조회 병목을 100만 건에서 찾은 일

문제

댓글 1,000건은 전부 메모리에 올라가서 인덱스가 없어도 0.3ms면 끝났습니다. 실제로는 인기글 하나에 댓글이 몰리기 때문에, 댓글 10%가 한 글에 쏠리도록 1천 건부터 100만 건까지 데이터를 만들어 다시 쟀습니다.

검토한 방법
  • 기각
    전부 읽어서 메모리에서 조립 · 첫 응답 210KB
  • 기각
    ROW_NUMBER 윈도우 함수 · 대댓글 2,000건을 다 정렬
  • 채택
    원댓글 20개씩 + 대댓글은 5개까지만 · 원댓글마다 5건 읽고 멈춤
해결

원댓글은 커서 방식으로 20개씩 가져오고 LATERAL 조인으로 원댓글마다 대댓글을 5개까지만 읽게 했습니다. 나머지 대댓글은 더보기 API로 나눴습니다. EXPLAIN ANALYZE로 실제로 5건에서 멈추는지 확인했습니다.

정렬까지 없애려면 인덱스 컬럼을 하나 더 늘려야 했습니다. 그러면 댓글을 쓸 때마다 비용이 커져서, 1.5ms 이하의 정렬은 그대로 두기로 했습니다.

결과

원댓글 첫 페이지 226.22ms → 36.58ms. 대댓글 5개 조회는 1천 건이든 100만 건이든 0.48ms로 같았습니다.

배포 · 복구

서버에서 직접 빌드하다 디스크가 99% 찬 배포 방식을 바꾼 일

문제

메모리 2GB짜리 EC2에서 도커 이미지를 빌드했더니 빌드 캐시가 24GB 쌓여 남은 디스크가 287MB였습니다. 이미지 태그도 latest 하나라서 문제가 생겨도 직전 버전으로 정확히 돌아갈 수 없었습니다.

검토한 방법
  • 기각
    서버 빌드 유지 + 캐시 정리 · 빌드할 때마다 결과가 달라짐
  • 기각
    ECR에 latest로 올리고 SSH로 배포 · 어느 버전으로 돌아갈지 모름
  • 채택
    Actions 빌드 + 이미지 해시 + SSM 배포 · SSH 포트와 고정 키가 필요 없음
해결

빌드는 GitHub Actions에서만 하고 이미지는 태그가 아닌 해시(digest)로 지정해 배포합니다. 서버 접속은 AWS SSM으로 바꿔 SSH 22번 포트를 닫았습니다. 오래 쓰는 액세스 키도 없애고 OIDC 임시 자격 증명을 씁니다. RDS 스냅샷으로 DB를 복구해 보는 연습도 했습니다.

배포 과정이 길어지고 AWS 설정이 늘었습니다. 혼자 운영하는 서비스라 문제가 생겼을 때 바로 되돌릴 수 있는 쪽이 더 중요했습니다.

결과

디스크 21GB를 비웠습니다. 직전 버전으로 되돌리는 데 19초 걸렸습니다.

그 밖에 푼 문제

외부 API를 기다리는 동안 DB 연결을 붙잡고 있던 카풀 비용 계산

기다리는 동안 DB 연결 점유 0ms, 저장할 때만 약 5ms+
문제

카풀 글을 쓰면 카카오 길찾기 API를 2번, 오피넷 유가 API를 1번 불러 1인당 비용을 계산합니다. 이 전체를 트랜잭션으로 묶으면 2~3초 동안 DB 연결을 잡고 있어서 10명만 동시에 써도 연결이 모자랐습니다.

검토한 방법
  • 기각
    서비스 전체에 트랜잭션 · DB 연결이 바닥남
  • 기각
    글 먼저 저장하고 비용은 나중에 계산 · 비용 없는 글이 보임
  • 채택
    외부 호출과 저장을 나눔 · 저장할 때만 연결 사용
해결

외부 API는 트랜잭션 밖에서 먼저 부르고 계산이 끝난 값만 저장하는 쪽에 넘겼습니다. 금액은 BigDecimal로 올림 규칙을 정해 계산하고 글과 함께 저장합니다. API가 실패하면 직접 입력으로 넘어갑니다. 유가는 Caffeine 캐시에 둡니다.

카카오모빌리티 · 오피넷 · Caffeine · PR #34

서버 한 대로 실시간 채팅을 몇 명까지 받을 수 있는지 먼저 잰 일

200명 × 5라운드, 메시지 20만 건 누락 0건 · 수신 지연 p95 951ms+
문제

채팅은 접속자가 늘면 보내야 할 메시지가 제곱으로 늘어납니다. Redis를 붙이기 전에 지금 서버로 어디까지 버티는지부터 알아야 했습니다.

검토한 방법
  • 기각
    Redis Pub/Sub부터 도입 · 아직 필요 없는 인프라
  • 기각
    대화를 전부 DB에 저장 · 게시글과 DB 연결을 나눠 씀
  • 채택
    기본 브로커 + 최근 30건만 메모리에 · 부하 테스트로 한계를 잼
해결

100명부터 400명까지 5단계로 부하를 걸어 안전한 선을 200명으로 정했습니다. 넘으면 스키장별로 채팅방부터 나누고 Redis는 그다음에 붙일 계획입니다. 기록에는 대화 내용을 빼고 입장과 퇴장만 남겨 로그 양을 96% 줄였습니다.

비밀번호 재설정 응답 속도로 가입 여부가 드러나던 문제

응답 내용과 시간 어느 쪽으로도 가입 여부를 알 수 없게 막음+
문제

가입된 이메일은 메일 발송 때문에 약 350ms, 가입 안 된 이메일은 5ms 만에 응답했습니다. 안내 문구를 똑같이 맞춰도 응답 시간만 보면 가입 여부를 알 수 있었습니다.

해결

가입 여부와 상관없이 같은 응답을 줍니다. 응답 시간도 최소 400ms에 0~100ms를 무작위로 더해 맞췄습니다. 인증 코드는 해시로 저장해 비교합니다. 비밀번호를 바꾸면 그 계정의 로그인 세션과 채팅 연결을 모두 끊습니다.

정상 사용자도 0.4초쯤 기다리게 됩니다. 비밀번호 재설정은 자주 쓰는 기능이 아니라서 괜찮다고 봤습니다.
